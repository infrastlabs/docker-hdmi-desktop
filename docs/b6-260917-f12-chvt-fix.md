# b6-260917 | f12 切 tty1 脚本修复明细（evtest|grep 管道 bug）

## 一、背景

HDMI 黑屏急救通道：监听键盘 F12，切换到 tty1。

| 脚本 | 用途 | 监听范围 |
|------|------|----------|
| `src/bin/f12_single.sh` | 选一个键盘，F12 → `chvt 1` | 单设备 |
| `src/bin/f12_to_tty1.sh` | 并发监听所有键盘，F12 → `chvt 1` | 全设备 |

## 二、Bug 现象

- `f12_single.sh`：evtest 匹配到 F12 后，最后的 `echo` / `chvt` 不执行，脚本直接退出
- `f12_to_tty1.sh`：F12 匹配后 TRIGGER 不写入，主循环 `while [ ! -s "$TRIGGER" ]` 死等，chvt 永不触发

## 三、根因

两脚本共用同一段有缺陷的管道模式：

```bash
evtest "$dev" | grep -m1 --line-buffered -E "type 1 \(EV_KEY\), code 88 \(KEY_F12\), value 1"
```

`grep -m1` 匹配第一行后立即退出 → 管道读端关闭。此时 evtest 有两种命运：

| 场景 | 行为 | 后果 |
|------|------|------|
| **SIGPIPE**：evtest 正写管道 | 收到 SIGPIPE 被杀，退出码 141 | `pipefail` 使 pipeline 返回 141（非零） |
| **挂起**：evtest 阻塞在 read() 等下一事件 | 不写管道、不被杀，继续运行 | bash 等 pipeline 所有成员 → **永久挂起** |

由此导致：

- `f12_single.sh`：`set -euo pipefail` → pipeline 141 → `set -e` 直接退出（场景1）；或 pipeline 挂起（场景2）
- `f12_to_tty1.sh`：子 shell 内 `if [ $? -eq 0 ]` → `$?` 为 141 非 0 → TRIGGER 不写入（场景1）；或子 shell 挂死在 pipeline（场景2）

> 场景2 是关键坑：**不是缓冲问题**。此前尝试的 `stdbuf` / `script`（deepseek 建议的修法 A/B）都无效，因为它们解决的是行缓冲，而真正问题是读端关闭后 evtest 的行为不可控。

## 四、验证（本地模拟）

```bash
# 场景1: SIGPIPE -> pipefail 141 -> set -e 退出, 后续代码不执行
set -euo pipefail
seq 1 1000000 | grep -m1 "500000" > /dev/null   # rc=141, echo 不打印

# 场景2: 写入者阻塞(模拟 evtest 等事件), pipeline 挂起 — 即使 || true 也死锁
timeout 3 bash -c 'set -euo pipefail; \
  (echo "type 1 (EV_KEY), code 88 (KEY_F12), value 1"; sleep 300) \
  | grep -m1 "code 88" || true; echo reached'
# 结果: EXIT=124 (timeout 杀死), "reached" 未打印 => 死锁确认
```

## 五、修复方案

### 1、原则

不用 `evtest | grep` 管道。改为：

1. evtest 后台运行，输出重定向到**独立日志文件**（无 SIGPIPE）
2. 轮询 `grep -qm1` 匹配日志文件，同时 `kill -0` 检测 evtest 提前退出
3. 匹配后**显式 kill evtest**（解决阻塞挂起，不依赖 SIGPIPE 自杀）

### 2、f12_single.sh（保留原样，仅加 `|| true`）

```bash
sudo evtest "$KEYBOARD_DEV" \
  | grep -m1 --line-buffered -E "..." \
  || true
```

- 已实测可用的临时修复：覆盖场景1（SIGPIPE 141）
- **局限**：场景2（evtest 阻塞）仍会挂起——因用户实测无碍，暂不改动

### 3、f12_to_tty1.sh（根治）

```bash
out="$WORKDIR/ev-${dev//\//_}"                       # 每键盘独立日志
pattern="type 1 \(EV_KEY\), code ${TARGET_CODE} \([A-Z0-9_]+\), value 1"
evtest "$dev" > "$out" 2>/dev/null &
ev_pid=$!
while ! grep -qm1 -E "$pattern" "$out" 2>/dev/null; do
    kill -0 "$ev_pid" 2>/dev/null || break           # evtest 提前退出
    sleep 0.05
done
if grep -qm1 -E "$pattern" "$out" 2>/dev/null; then
    printf '%s  |  %s\n' "$dev" "$name" > "$TRIGGER"
fi
kill -TERM "$ev_pid" 2>/dev/null                     # 显式杀, 防挂起
```

要点：
- 轮询间隔 0.05s，F12 按下到 chvt 总延迟 < 0.3s
- evtest 输出即时落盘（实测管道可匹配，说明无 libc 全缓冲问题）
- TRIGGER 写入条件保留原语义：evtest 提前退出（无匹配）不误触发

## 七、结论

- 两脚本均已实测可用
- 教训：`producer | grep -m1` 模式在 producer 不会自然退出时（守护型命令），读端关闭后 producer 行为不可控（SIGPIPE 或挂起），应避免；改为文件+轮询+显式 kill

### 1、f12_single.sh 根治版（与 f12_to_tty1 相同思路）

```bash
LOG=$(mktemp /tmp/f12-XXXXXX.log)
pattern="type 1 \(EV_KEY\), code $TARGET_CODE \([A-Z0-9_]+\), value 1"
sudo evtest "$KEYBOARD_DEV" > "$LOG" 2>/dev/null &
ev_pid=$!
while ! grep -qm1 -E "$pattern" "$LOG" 2>/dev/null; do
    if ! kill -0 "$ev_pid" 2>/dev/null; then
        echo "evtest 提前退出" >&2
        rm -f "$LOG"
        exit 1
    fi
    sleep 0.05
done
pkill -TERM -P "$ev_pid" 2>/dev/null   # sudo 的子进程 evtest
kill -TERM "$ev_pid" 2>/dev/null       # sudo
rm -f "$LOG"
```

### 3、最终状态

- 两脚本均以「日志文件 + 0.05s 轮询 + 显式 kill」根治，SIGPIPE(141) 与阻塞挂起两种失败模式均覆盖

## 九、并行多跑可行性

### 1、结论

两脚本均可各自并行多跑：同脚本多开、两脚本混跑均安全，可用于急救冗余。

### 2、安全性依据

- **临时文件隔离**：f12_single 用 `mktemp /tmp/f12-*.log` 唯一日志；f12_to_tty1 用 `mktemp -d` 独立 WORKDIR（日志/TRIGGER 各自目录）
- **进程隔离**：kill 均基于精确 pid / 父 pid（`pkill -P`），不会跨实例误杀
- **input 广播式监听**：无 `--grab` 时多进程可同时 open 同一键盘，都能收到同一事件，互不独占
- **chvt 幂等**：多实例同时触发只是重复切到同一 tty（当前 `TARGET_TTY` 硬编码为 1），无害

### 3、注意事项

- 不要用 `evtest --grab` 独占设备（会导致其他监听者收不到事件）
- 若将来参数化 `TARGET_TTY` 且不同实例切不同 tty，会互相覆盖（最后执行者生效）
- f12_single 多实例首次并发 `sudo` 可能需多次输密码，可先 `sudo -v` 一次建立缓存
- 资源开销：每实例每键盘 1 个 evtest 进程 + 0.05s 轮询，多开几个可忽略
